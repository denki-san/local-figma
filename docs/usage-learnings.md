# Figma 本地 CLI 桥接使用心得

记录日期：2026-09-17

## 核心结论

这套桥接方案非常适合在现有 Figma 稿上做精确修改。要从零设计出高质量 UI，还需要补一层设计上下文、产品语义和视觉评审能力。

它最有开源价值的部分，是一套让 Agent 安全、持续、可检查、可回滚地编辑本地 Figma 文件的运行时与工作流。

建议定位：

> 面向 Agent 的本地 Figma 编辑运行时，而不是自动设计工具本身。

## 已验证的优势

- 完全本地运行：CLI、桥接服务和 Figma Development Plugin 都在本机，通过 `127.0.0.1` 通信，不依赖付费 Figma API。
- Plugin API 覆盖完整：文字、图层、Auto Layout、图片填充、组件、变量、原型属性都能直接操作。
- 结果保留为原生 Figma 图层：文字、Frame、图片、组件和层级关系可继续编辑。
- 适合 Agent 调用：Agent 生成本地 JavaScript，通过 CLI 执行，返回节点 ID 和结构化结果。
- 修改过程可追踪：每次需求对应一个脚本，可重新执行、检查和回溯。

## 关键问题与经验

### 1. 设计效果取决于上下文质量

只提供一个节点和一句“改一下”时，Agent 只能看到局部，容易做出视觉上合理、产品语义错误的方案。

本次典型误解包括：

- 把 Markdown 开头截取部分理解成独立的“首页摘要”。
- 把程序生成区画成与 Markdown 并列的正文内容。
- 为解释结构增加过多说明卡片。

真实关系是：

```text
一份 Markdown
├── 开头若干行 → 首页卡片
└── 完整内容 → 查看工作说明 / 完整长图

程序生成区
└── 根据 Markdown 自动生成，不属于 Markdown 正文
```

桥接工具需要保存节点结构，也需要保存产品语义、数据来源、区域关系和不可编辑边界。

### 2. 坚持小步修改与截图检查

Plugin API 返回成功，只能证明属性写入完成，不能证明设计正确。

实际出现过的问题：

- 文字字号混合。
- 文字覆盖底部技能标签。
- 编号在圆形标签中换行。
- 长图错误使用精简内容。
- 固定区域结构存在，滚动效果仍未生效。

可靠流程：

1. 读取目标节点结构。
2. 只修改一个明确区域。
3. 返回全部变更节点 ID。
4. 导出目标区域截图。
5. 检查截断、重叠、字号、层级和滚动。
6. 通过后再进入下一批修改。

### 3. Figma 属性存在隐含关系

- `Truncate text` 依赖正确的文本 resizing 模式。
- `Max lines` 需要与文本高度模式配合。
- `Clip content` 属于外层 Frame。
- 单个 Text 图层也可能含 Mixed 字号、字重和行高。
- 固定滚动子层在旧 Group 结构中表现不稳定。

本次 `numberOfFixedChildren` 写入后仍返回 `0`，最终改用结构保证：

```text
抽屉
├── 独立滚动视口
├── 固定逻辑图区
└── 固定操作栏
```

固定区域成为滚动视口外的同级顶层，从结构上保证不会滚动。

### 4. 优先隐藏旧节点

Agent 可能误解需求。旧节点直接删除会增加恢复成本。

稳妥策略：

- 默认把旧节点隐藏或移动到回滚区。
- 新版本使用清晰、稳定的名称。
- 修改脚本保持幂等或至少可检测重复执行。
- 验证稳定后再显式清理旧节点。

这相当于为 Figma 编辑提供轻量事务与恢复能力。

### 5. 图层命名是 Agent 可维护性的基础

`Frame 723`、`Frame 1106` 会让 Agent 每次重新理解结构。下列名称明显提高了维护效率：

- `工作说明 Markdown｜精简四段`
- `固定吸底逻辑图区｜Top layer`
- `固定高度正文区｜Clip content`
- `完整 Markdown 原文｜长图展示`

有意义的命名应成为默认验证规则。

### 6. 上下文分为四层

1. 画布上下文：节点树、尺寸、坐标、组件、变量和文字样式。
2. 视觉上下文：修改前后截图、参考页面和设计系统。
3. 业务上下文：需求文档、会议记录、数据来源、可编辑区和程序生成区。
4. 历史上下文：执行脚本、节点 ID、修改原因、结构 diff 和验证结果。

开源版本应通过项目级 `context.json` 和逐次 run artifact 自动保存这些信息。

### 7. 从零设计需要上层能力

桥接层解决“怎样操作 Figma”，不会自动解决“怎样做好设计”。从零设计仍需要：

- 设计系统组件检索与复用。
- 页面结构规划。
- 同类页面视觉参考。
- 自动对齐、间距和字体检查。
- 截图差异比较。
- 产品语义约束。

## 历史使用记录汇总

### 已成功验证

- 主链路为：任务脚本 → 本机 CLI → `127.0.0.1` bridge → Figma Development Plugin → Figma Plugin API。
- 成功创建过两个可编辑的原生首页候选方案，并读回尺寸、圆角、原型 reactions 和关键节点。
- 原型验证需要真实点击；存在 reactions 只能证明连线属性存在。
- 已将通用流程固化为本机 `figma-plugin-cli` skill，并通过回环模拟验证认证、入队、执行、目标校验、结果回传和退出清理。
- Local Design Bridge 只是通信通道。没有任务运行时可以关闭；关闭不会删除已有设计，会中断当前或后续自动修改。

### 已暴露的失败样本

- `pollAgeMs: null` 表示插件没有形成有效连接。
- Figma Development 菜单可能保留失效的同名插件注册；“已导入”不等于当前 manifest 已加载。
- `submit` 返回 job ID 只表示入队；必须读取对应 `result` 并确认 `ok`。
- 一次功能优先设计只完成 3/8 个画板，且没有完成本地 CLI 结果验证，因此不能将部分生成描述为完整交付。
- 任务专属 file key、页面 ID、路径和临时 token 不能固化进通用工具。

### 稳定的执行守则

- 每次运行使用独立任务目录和临时令牌。
- 执行前重新验证文件名、file key、页面名和页面 ID。
- 只监听本机回环地址。
- 先取得新鲜 poll，再提交任务。
- 超时或断连时先读回文档状态，禁止盲目重放创建脚本。
- 先 `loadFontAsync` 再写文字。
- 新插件按 dynamic page loading 编写，页面读取和部分样式、reactions 操作使用异步 API。
- computer use 只负责打开插件、视觉检查和真实点击验证。
- 临时令牌、session 文件和生成后的带令牌 UI 不进入版本库。

## 下一版优先能力

- `inspect`：输出紧凑、稳定、带语义的节点树。
- `snapshot`：修改前保存结构快照和目标截图。
- `diff`：展示新增、修改、隐藏、移动和删除的节点。
- `rollback`：恢复上一次受保护操作。
- `validate`：检测文字溢出、重叠、Mixed 字号、越界和无意义命名。
- `context.json`：记录产品语义、数据来源、区域关系和不可编辑边界。
- `design-system`：查找相邻页面已使用的组件、变量和样式。
- `preview`：执行后自动导出目标区域截图。
- `transaction`：在明确的 Undo 边界中执行并验证，失败时受保护地撤销。
